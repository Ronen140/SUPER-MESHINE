# תוכנית פיתוח — מערכת חשבוניות וקבלות

**תאריך:** 2026-08-30 · **סטטוס:** טיוטה לאישור המייסד
**מבוסס על:** [[2026-08-30-invoicing-services-feature-benchmark]] (בנצ'מרק פונקציות של Morning, iCount, Sumit, EZcount, Ypay, Invoice4U) ו-[[2026-08-30-invoicing-ui-design-research]] (תחקיר נראות ועיצוב), שניהם ב-`vault/Discovery/`.

---

## 1. מה בונים ולמה

מערכת הפקת מסמכים חשבונאיים **רב-עסקית** למייסד (עוסק פטור) ולחבריו (בהם עוסק מורשה) — חינמית לתפעול, נקייה ויפה, שפותרת את הכאב שהשירותים בתשלום לא פתרו: **פירוט עבודה עשיר ופריטים מוגדרים מראש שסכומם נשאר פתוח עד ההפקה**.

התובנה מהבנצ'מרק: העסקים משלמים 350–1,200+ ₪/שנה על פונקציונליות שהיא ברובה CRUD + PDF + חתימה + API אחד של רשות המסים. המודל העסקי של כל השוק בנוי על עמלות סליקה — ולכן סליקה אינה חלק מהמערכת שלנו (רישום תקבולים בלבד).

## 2. עקרונות מנחים

1. **חוקי קודם כל:** מסמך שהופק הוא immutable, מספור רציף פר סוג מסמך, ביטול רק בזיכוי מקושר, ארכיון 7 שנים, כיתוב "מסמך ממוחשב". אלו דרישות הוראות ניהול ספרים — לא פיצ'רים.
2. **סוג הישות קובע את המסמכים:** עוסק פטור מפיק קבלה / חשבונית עסקה / הצעת מחיר בלבד (לעולם לא חשבונית מס); עוסק מורשה מפיק את הסט המלא עם מע"מ.
3. **Multi-business עם בידוד מלא:** כל עסק — מספור, לקוחות, קטלוג והרשאות נפרדים; RLS בכל טבלה (עקרון SUPER-MESHINE #1); audit log על כל mutation (עקרון #2).
4. **מהירות כפיצ'ר:** קבלה ללקוח קיים ב-≤20 שניות. זה מה שהפך את Morning למובילה.
5. **נראות:** "השקט של Stripe, החום של Morning" — מפרט מלא בדוח העיצוב, תמצית בסעיף 6.

## 3. Stack (מומלץ — לאישור)

- **אפליקציה:** Next.js 15 (App Router) + TypeScript, `dir="rtl" lang="he"`.
- **UI:** shadcn/ui + Tailwind v4 (logical properties בלבד), TanStack Table, react-hook-form + zod.
- **DB/Auth/Storage:** Supabase (Postgres + RLS + Auth + Storage ל-PDF-ים). Free tier מכסה בקלות את הנפח (~2 מסמכים/חודש לעסק).
- **PDF:** רינדור HTML→PDF בצד שרת עם פונט Assistant מוטמע.
- **Hosting:** Vercel free tier. **עלות שוטפת: ₪0** (למעט חריג אפשרי — ראה סיכון החתימה בסעיף 8).
- **מיקום בקוד:** נשאר ב-`invoicing-receipts/` כפרויקט pnpm עצמאי (מחוץ ל-workspace של ה-ERP). אם יוחלט בעתיד שזה מודול Billing של SUPER-MESHINE — יועבר ל-`apps/`.

## 4. שלבי הפיתוח

### Phase 0 — שלד ותשתית
Scaffold של האפליקציה, Supabase project, סכמת בסיס + RLS + audit log, אימות משתמשים, יצירת עסק ראשון, business switcher. **DoD:** משתמש נרשם, יוצר עסק, מחליף בין עסקים; RLS מוכח בבדיקה.

### Phase 1 — MVP לעוסק פטור (המשתמש הראשון: המייסד)
- כרטיסי לקוח (שם, ח.פ/ע.מ/ת.ז, מייל, טלפון, תנאי תשלום).
- **קטלוג פריטי עבודה:** שם + תיאור מפורט מרובה-שורות + מחיר ברירת-מחדל *אופציונלי*; פריט שנוצר תוך כדי עריכת מסמך נשמר לקטלוג.
- **עורך מסמכים split-view עם live preview** — טיוטה נשמרת אוטומטית, הכל עריך עד "הפקה"; הפקה = מספר רציף + נעילה + PDF חתום + כיתוב "מסמך ממוחשב".
- מסמכים: **קבלה** (עם פירוט אמצעי תשלום: מזומן/צ'ק/העברה/אשראי/ביט), **חשבונית עסקה**, **הצעת מחיר**. ביטול קבלה — במסמך נגדי מקושר.
- שליחה במייל + עמוד צפייה ציבורי למסמך + הורדת PDF; מנגנון הסכמת לקוח למסמכים ממוחשבים (חד-פעמי).
- דשבורד: הכנסות החודש, ממתין לתשלום, טיוטות, מסמכים אחרונים.
- **DoD:** המייסד מפיק קבלה אמיתית ראשונה מהמערכת והרו"ח שלו מאשר שהיא תקינה.

### Phase 2 — עוסק מורשה + חשבוניות ישראל
- חשבונית מס, חשבונית מס-קבלה, חשבונית זיכוי (מקושר לאב); חישוב מע"מ (מלא 18% / אפס / פטור) לפי תאריך המסמך; ניכוי מס במקור בקבלות (ברוטו/ניכוי/נטו, שיעור פר לקוח).
- **אינטגרציית מספר הקצאה מול API רשות המסים** — ממצא קריטי מהבנצ'מרק: הסף הואץ ל-**10,000 ₪ מ-1.1.2026 ו-5,000 ₪ (לפני מע"מ) מ-1.6.2026**, כלומר כמעט כל חשבונית B2B של החבר המורשה דורשת מספר הקצאה כבר היום. כולל: הטבעה על המסמך, זיכויים מעל הסף, וטיפול בסירוב/אי-זמינות API (חשבונית לא מופקת בלי הקצאה כשנדרשת — נשארת טיוטה עם התראה).
- **DoD:** החבר המורשה מפיק חשבונית מס עם מספר הקצאה אמיתי (סביבת ה-sandbox של רשות המסים תחילה).

### Phase 3 — דוחות וייצוא
- דוח הכנסות תקופתי, דוח מע"מ, מסמכים פתוחים + aging (0-30/31-60/61-90+).
- **ייצוא במבנה אחיד (BKMVDATA + INI)** — גם דרישת ביקורת מס וגם "תעודת ביטוח" ליציאה מהמערכת. ייצוא/דוח חודשי לרו"ח.
- **DoD:** קובץ מבנה אחיד נפתח תקין בבודק של רשות המסים / אצל הרו"ח.

### Phase 4 — נוחות (לפי ביקוש מהחבורה)
מסמכים חוזרים (הוראת קבע), תזכורות תשלום אוטומטיות, מסמכים באנגלית + מט"ח (שער בנק ישראל), תעודות משלוח/הזמנות עבודה, ניהול הוצאות, PCN874, החתמת לקוח על הצעת מחיר, WhatsApp.

**מה במודע לא בונים:** סליקה בפועל, מסלולי תמחור/מנויים, marketplace. רישום במרשם התוכנות של רשות המסים לא נדרש לשימוש עצמי (נדרש רק אם נפיץ לאחרים — ואז נהיה מוכנים כי מבנה אחיד כבר בנוי).

## 5. מודל נתונים ראשוני (ל-review של ה-architect)

`users` · `businesses` (סוג ישות: פטור/מורשה, פרטי עסק, לוגו, צבע אקצנט) · `business_members` (הרשאות) · `customers` · `items` (קטלוג, מחיר אופציונלי) · `documents` (סוג, סטטוס טיוטה/הופק/מבוטל, מספר רציף, מספר הקצאה, קישור למסמך אב) · `document_lines` (תיאור עשיר, כמות, מחיר, הנחה) · `payments` (רכיבי תקבול בקבלה) · `document_counters` (מונה רציף פר עסק+סוג+שנה, עם נעילת transaction) · `audit_log` · `allocation_requests` (בקשות הקצאה: סטטוס, תשובת API). כל הטבלאות עם `business_id` + RLS.

## 6. שפת עיצוב (תמצית — המפרט המלא בדוח העיצוב)

| נושא | החלטה |
|---|---|
| פלטה | ניוטרל stone חמים, primary אחד — emerald/teal עמוק; צבעים סמנטיים רק לסטטוס (שולם/ממתין/באיחור/טיוטה) |
| פונט | Assistant (fallback: Heebo, Noto Sans Hebrew), `tabular-nums` בכל עמודת סכומים |
| עורך | Split-view: טופס מימין, preview חי של המסמך משמאל (רפרנס קוד: Invoify — אותו stack) |
| דשבורד | stat cards + aging + מסמכים אחרונים; איור ורגש רק ב-empty states ומסכי הצלחה (בהשראת Morning) |
| Multi-business | Switcher בראש ה-sidebar (דפוס Notion), קונטקסט העסק גלוי תמיד, החלפה מנקה את כל המסך |
| PDF | A4 RTL נקי: לוגו ימין-למעלה, בלוק מסמך (מספר/תאריך/מקור-העתק/מספר הקצאה), טבלת פריטים, סיכום מע"מ, חתימה דיגיטלית; מצוין גם בהדפסת שחור-לבן |
| RTL | logical properties בלבד; כל מספר/תאריך/ח.פ ב-LTR isolation; `Intl.NumberFormat('he-IL')` לכל פורמט |

## 7. תהליך העבודה

כל Phase עובר את מסלול הבית: plan מפורט (writing-plans) → architect ל-schema ו-RLS → engineering-manager מפצל ל-backend-builder/frontend-builder → שרשרת QA (spec-reviewer → code-quality-reviewer → **erp-domain-expert חובה** על כל לוגיקת מס/מספור/זיכויים) → אימות בדפדפן → vault → commit → push.

## 8. סיכונים ושאלות פתוחות

1. **חתימה אלקטרונית מאובטחת (הסיכון המרכזי):** "מסמך ממוחשב" מחייב חתימה אלקטרונית מאובטחת/מאושרת בעת ההפקה. אצל הספקים זה שקוף כי הם חותמים בתעודה שלהם. ב-self-hosted ייתכן צורך בתעודה בתשלום (למשל Comsign) — עלות חד-פעמית/שנתית שעשויה לסדוק את ה"חינם לגמרי". **לברר מול רו"ח לפני Phase 1** מה נדרש בפועל לעוסק פטור שמפיק קבלות. חלופת ביניים: הדפסה ותיוק כמסמכי נייר עד שתוסדר חתימה.
2. **אישור רו"ח:** כל עסק בחבורה מוודא מול הרו"ח שלו שהוא מקבל מסמכים מהמערכת (DoD של Phase 1).
3. **API רשות המסים:** דורש הרשמה ו-OAuth מול שער ממשלתי; מ-2025 בקשות הקצאה נבחנות ולא מאושרות אוטומטית — התוכנית כוללת טיפול בסירוב, אך תהליך ההרשמה עצמו טרם נחקר לעומק.
4. **ספי ההקצאה אומתו ממקורות משניים** (אתרי הספקים חסומים ל-crawling) — לוודא את לוח הזמנים הסופי מול gov.il לפני מימוש Phase 2.
5. **תקרת עוסק פטור** (122,833 ₪ ב-2026): המערכת יכולה להתריע כשמתקרבים — nice-to-have ל-Phase 4.

## 9. הצעד הבא

אישור המייסד על: (א) ה-stack, (ב) חלוקת הפאזות, (ג) בירור החתימה הדיגיטלית מול רו"ח. עם האישור — Phase 0 יוצא לדרך דרך ה-architect (schema + RLS).
